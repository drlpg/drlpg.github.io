Docker 多阶段构建：把 Next.js 生产镜像从 1GB+ 瘦到 200MB 以内

发表于2026-11-16|更新于2026-11-16|部署
|总字数:2.4k|阅读时长:8分钟|浏览量:
文章摘要

给 Next.js 应用写 Dockerfile，最常见的写法是这样的：

能跑，但镜像动不动就 1GB 以上。原因不难猜：源码、构建工具、开发依赖、整份 node_modules 全打进去了——而运行时真正需要的，只是一小部分。

瘦身的办法是两件套：Next.js 的 standalone 输出 + Docker 多阶段构建。下面按这个顺序讲。

第一步：打开 standalone 输出

默认情况下，next build 假设运行时整份 node_modules 都在。打开 output: 'standalone' 后，构建会追踪每条路由实际用到的文件，只把这些文件和一个精简的 server.js 复制到 .next/standalone/ 里：

构建后看一下产物结构：

有两件事要注意：

  1. public/ 和 .next/static/ 不在 standalone 文件夹里。Next.js 默认假设这些静态资源由 CDN 提供。没有 CDN、要靠容器自己 serve 的话，必须在 Dockerfile 里手动把它们拷进去，漏了就会出现图片、CSS 404。
  2. 启动命令是 node server.js，不是 next start。用 next start 跑 standalone 产物会收到警告，server.js 本身就是可直接运行的服务器入口。PORT 环境变量可以改监听端口，默认 3000。

第二步：三阶段 Dockerfile

下面这份结构取自 Next.js 官方 with-docker 示例的思路，只把 Node 版本换成了当前 LTS。三个阶段各干一件事：装依赖、构建、运行，只有最后一个阶段会成为最终镜像。

逐段解释为什么这样写：

  • 三个阶段分工明确。deps 只装依赖，builder 只构建，runner 从干净的基础镜像重新开始，只拷 standalone 产物。编译器、开发依赖、源码都不会进入最终镜像。
  • 先拷 package.json 和 lockfile 再装依赖。只要这两个文件没变，Docker 层缓存就会复用 deps 阶段，改代码时只重跑 builder，构建明显变快。
  • --mount=type=cache 缓存 npm 下载。需要 BuildKit（Docker 23+ 默认开启），npm ci 不用每次都重新下载全部包。
  • 用 node:26-slim 做基础镜像。Node 26（Lithium）自 2026 年 10 月 28 日起是 Active LTS，支持到 2029 年 4 月 30 日；Node 24 仍在维护期，支持到 2028 年 4 月 30 日；Node 20 及更早版本已停止维护。slim 是基于 Debian 的精简镜像，比完整版小得多，又避开了 Alpine 的 musl 兼容问题（见下文）。Next.js 16 要求 Node 不低于 20.9，选 LTS 线即可。
  • 以非 root 用户运行。官方 Node 镜像自带 node 用户，COPY --chown=node:node 让拷进去的文件归它所有，再 USER node 切换过去。注意 public/ 也要带 --chown——容器以非 root 用户运行时，未 chown 的静态文件可能读不到，表现为图片 403/404，这个坑很隐蔽。
  • HOSTNAME="0.0.0.0" 让 server.js 监听所有网卡，否则容器外的请求进不来。

第三步：写好 .dockerignore

多阶段构建再干净，也架不住构建上下文里塞满垃圾。COPY . . 会把上下文里的所有文件先送进构建，.next/、.git/ 动辄几百 MB，既慢又可能把本地构建产物、环境变量文件误带进镜像：

核心是三条：node_modules、.next、.git。.env* 也要排除——密钥绝不能进镜像，运行时用 --env-file 或编排工具注入。

能瘦到多少：一次公开实测

以下是一次公开实测的数据（2026 年 10 月，新建的 Next.js 16.4 应用，TypeScript + Tailwind + App Router，同一台机器，三种写法都返回 HTTP 200）：

写法 镜像体积
单阶段（node:24，COPY 全量 + 构建） 1.77 GB
三阶段 standalone（node:24-slim） 268 MB
三阶段 standalone（node:24-alpine） 209 MB

实际数值因项目依赖而异，但量级关系是稳定的：standalone + 多阶段能把镜像压到原来的六分之一到八分之一。体积小的好处不只是省磁盘：镜像拉取更快、部署更快、攻击面更小（最终镜像里没有编译器和源码）。

Alpine 还是 slim？

Alpine 还能再省几十 MB，但它用的是 musl 而不是 glibc，带原生依赖的包可能出问题。最常见的是图片处理库 sharp：Alpine 下 npm 会装它的 musl 构建（@img/sharp-linuxmusl-x64），多数项目能正常工作，但一旦有某个原生包没有 musl 预编译版，就得在 Alpine 里现场编译，构建变慢还容易失败。

我的建议：

  • 默认用 node:26-slim。268 MB 这个量级已经足够好，兼容性最稳。
  • 确认没有原生依赖问题后，再试 Alpine。换之前先在 Alpine 镜像里跑通一次完整构建和图片优化，确认无报错再切。
  • 不要用完整版 node:26 做最终镜像。它带了完整的 Debian 工具链，体积大、攻击面大，只适合本地开发。

环境变量的陷阱：构建时 vs 运行时

这是多阶段构建最容易踩的坑，表现是：应用能构建、容器能启动，但某个配置在生产环境是 undefined。

Next.js 的环境变量分两类，分界线在构建时刻：

类型 读取时机 怎么传进容器
NEXT_PUBLIC_* 构建时固化进 JS 产物 构建参数 --build-arg
其他变量（如数据库地址） 运行时读取 docker run -e 或 --env-file

对应的 Dockerfile 里要在构建阶段声明：

还有一个细节：完全静态预渲染的页面在构建时就把变量读走了，运行时再改变量也不会影响它。如果某个值必须在运行时才能确定（比如不同环境共用一个镜像），就别把它放进会被预渲染的页面，或者改用服务端组件在请求时读取。

构建缓存：让重复构建更快

镜像瘦了，构建速度也值得顺手优化。两个关键点：

  1. 依赖层与代码层分离。上面 Dockerfile 的写法已经做到了：package.json 和 lockfile 不变，deps 阶段直接命中缓存；只有改了代码才重跑 builder。反过来，如果先 COPY . . 再 npm ci，任何一次代码改动都会让依赖层失效，每次构建都重装全部依赖。
  2. CI 里复用构建缓存。GitHub Actions 构建镜像时，用 docker/build-push-action 的 cache-from / cache-to（type=gha），跨运行复用层缓存。没有缓存时，一次完整构建里 npm ci 和 next build 是最耗时的两步。

验证缓存是否生效很简单：连续构建两次，第二次应该只有少量步骤显示 CACHED 以外的输出——如果每次都从头装依赖，检查 COPY 的顺序是不是写反了。

常见报错排查

现象 原因 解决
图片、CSS 404 漏拷 public/ 或 .next/static/ 按上文 Dockerfile 补两行 COPY
next start 警告 standalone 产物不该用 next start 改用 node server.js
容器启动后连不上 server.js 只监听了回环地址 设 HOSTNAME="0.0.0.0"
静态文件 403/404 以非 root 用户运行，但文件没 chown COPY 加 --chown=node:node
构建每次都重装依赖 COPY . . 写在 npm ci 之前 先拷 lockfile 装依赖，再拷源码
某个配置生产环境是 undefined NEXT_PUBLIC_* 没在构建时传入 用 --build-arg 在构建时传
Alpine 下 sharp 报错 musl 缺少预编译包 换 slim 镜像，或确认 musl 构建可用

验证：构建并跑起来

再顺手检查两点：镜像里不该有源码（docker run --rm my-app ls /app 应该只有 server.js、node_modules、public、.next）；容器进程不是 root（docker exec <容器名> whoami 应输出 node）。

总结

  • 开 output: 'standalone'，让 Next.js 只追踪运行必需的文件。
  • 三阶段 Dockerfile：deps 装依赖、builder 构建、runner 只装 standalone 产物 + public + .next/static。
  • .dockerignore 排除 node_modules、.next、.git、.env*。
  • 基础镜像默认选 node:26-slim，确认无原生依赖问题再试 Alpine。
  • NEXT_PUBLIC_* 构建时用 --build-arg 传，运行时变量用 --env-file 传，两类不要混。
  • 以非 root 用户运行，COPY 记得 --chown=node:node。

一套组合拳下来，生产镜像从 1GB 以上降到 200MB 左右，部署拉取更快，攻击面也更小。下一篇可以接着讲：镜像瘦了之后，用 GitHub Actions 把“构建—推送—部署”串成一条自动流水线。
