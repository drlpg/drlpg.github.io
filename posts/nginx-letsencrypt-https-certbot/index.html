Nginx + Let's Encrypt：给网站配上 HTTPS，证书自动续期不用管

发表于2026-11-23|更新于2026-11-23|部署
|总字数:2.8k|阅读时长:9分钟|浏览量:
文章摘要

上一篇讲了怎么用 Nginx 给 Next.js 应用做反向代理，但那篇文章里的站点跑的还是 HTTP。HTTP 有两个现实问题：浏览器会在地址栏标“不安全”，用户不敢输密码、填表单；搜索引擎也明确把 HTTPS 作为排名信号之一。好在今天给网站上 HTTPS 不用再花钱买证书——Let’s Encrypt 免费签发，Certbot 全程自动，一台服务器十分钟就能搞定。

下面以前一篇的 Nginx 站点为例，从零配到自动续期。

先确认三个前置条件

动手之前先把这三件事对上，缺一个后面都会卡住：

  1. 域名已经解析到这台服务器。用 dig +short example.com 或 ping example.com 看返回的 IP 是不是服务器的公网 IP。域名没解析过来，Let’s Encrypt 连不上你的服务器，验证一定失败。
  2. Nginx 在跑，且 80 端口对外放行。Let’s Encrypt 用 HTTP-01 方式验证域名所有权：它会在你的服务器上放一个临时文件，再从公网经 80 端口来取。防火墙（UFW、云厂商安全组）把 80 封了，验证就过不去。配好 HTTPS 之后 80 端口也要留着——续期时每次验证都要走 80 端口，跳转到 HTTPS 即可，不要直接封掉。
  3. Nginx 里已经有一个能用的 HTTP 站点配置，server_name 写的是你要申请证书的域名。Certbot 的 Nginx 插件就是靠 server_name 找到要改的那个 server 块的。

注意：server_name 里把带 www 和不带 www 都写上，后面一次申请可以把两个名字签进同一张证书。

关键：自动续期是怎么工作的

证书到手只是完成了一半。Let’s Encrypt 的证书有效期只有 90 天，而且是故意设计成这么短的——有效期越短，私钥泄露后的危害窗口越小。手动续期每 90 天来一次不现实，所以自动续期不是“锦上添花”，而是这套方案成立的前提。

机制很简单，记住三个数字：

  • 90 天：证书有效期。
  • 30 天：剩余有效期少于 30 天时，续期任务才会真正去换新证书。
  • 每天两次：续期任务每天检查两次，证书还早就不动手，到期前 30 天才换。

也就是说证书实际大约在签发后第 60 天被换掉，留出整整 30 天的窗口给你发现并修复续期故障——前提是你真的去检查它在工作。

两个命令都应该返回 enabled / active。如果不是，用 sudo systemctl enable --now certbot.timer 把它拉起来，再复查一次。

演练续期：每个人都该跑一次

自动续期最大的坑，是装完从不验证，等证书过期那天才发现续期早就坏了。Certbot 提供了专门的演练命令，走一遍完整的续期流程——验证、插件、钩子全都真实执行——但只对接 Let’s Encrypt 的测试环境，不写真实证书、不消耗次数限制：

看到 Congratulations, all simulated renewals succeeded 才算过关。不要用 --force-renewal 来“测试”：那会签发一张真实证书，计入“同一域名组合每周最多 5 张重复证书”的次数限制，测几次就把额度烧光了。

建议把 dry-run 写进部署清单：新服务器配完 HTTPS 当天跑一次，之后每季度顺手跑一次。演练失败的两个最常见原因，后面排查表里有。

续期后 Nginx 怎么知道证书换了

证书文件换了，正在运行的 Nginx 还拿着旧证书在内存里——不重载，访客看到的还是快过期的那张。--nginx 插件签发的证书，Certbot 会在续期后自动帮 Nginx 重载，这一点不用操心。

但如果你用的是 certonly --webroot 这类不接管 Nginx 的方式，或者还有别的服务在读同一份证书（比如邮件服务、另一个反向代理），就要自己加部署钩子：

钩子脚本必须有可执行权限，且放在 renewal-hooks/deploy/ 目录下。dry-run 也会执行部署钩子，所以演练时就能发现钩子写错了——这也是演练的价值之一。

一个提醒：过期提醒邮件已经停了

Let’s Encrypt 自 2025 年 6 月起停止发送证书过期提醒邮件。以前续期坏了还能收到邮件兜底，现在不会再有任何通知——证书默默过期，访客先看到浏览器报错，你才知道。

所以自动续期不能只靠“装了定时器就完事”，至少要有一层外部监控：

  • 最简单的：用 UptimeRobot 这类免费监控服务，每 5 分钟请求一次你的 HTTPS 站点，证书过期会导致请求失败，直接触发告警。
  • 已经有服务器巡检习惯的：把 sudo certbot certificates 的过期时间加进巡检项，剩余有效期少于 25 天还没换新证书就该查了。

常见报错排查

现象 原因 解决
申请时报连接超时 / 验证失败 域名没解析到本机，或 80 端口被防火墙挡住 dig +short example.com 核对 IP；放行 80 端口（UFW：sudo ufw allow 80/tcp；云厂商：安全组放行）
certbot --nginx 找不到 server 块 server_name 与申请的域名对不上 检查 Nginx 配置里的 server_name 是否包含 -d 的域名；先 sudo nginx -t 确认配置本身没错
dry-run 失败，提示 80 端口连接被拒 配好证书后有人把 80 端口封了，或 Nginx 停了 80 端口必须保持开放并由 Nginx 监听，续期验证每次都要走 80；只做跳转，不要封端口
续期成功了，浏览器还是旧证书 Nginx 没重载 --nginx 插件一般会自动重载；certonly 方式要自己加 deploy 钩子；手动执行 sudo systemctl reload nginx 验证
报次数限制（too many certificates） 短时间内对同一域名组合重复签发 用 --dry-run 演练，不要用 --force-renewal 测试；等限制窗口过去（同一域名组合每周 5 张）
想加新域名到已有证书 证书签发时域名是固定的 用 --expand 重新签发：sudo certbot --nginx -d example.com -d www.example.com -d app.example.com --expand

还有两点容易踩：

  • 不要直接编辑 /etc/letsencrypt/live/ 里的文件。live 目录下的是指向 archive/ 的符号链接，Certbot 续期时只换链接目标；手动改文件或删旧证书，续期配置可能直接乱掉。查看证书用 certbot certificates，删除用 certbot delete --cert-name example.com。
  • 通配符证书（*.example.com）走不了 HTTP-01 验证，必须用 DNS-01，在 DNS 服务商处加 TXT 记录验证，Certbot 需要对应服务商的 DNS 插件（比如 python3-certbot-dns-cloudflare）。只有一个或几个固定子域名时，直接把子域名列进 -d 更简单。

总结

  • Let’s Encrypt 证书免费，Certbot 一条命令完成签发 + Nginx 配置 + HTTP 跳转，十分钟能跑通。
  • 前置条件三件套：域名解析到本机、80 端口放行、Nginx 里有对应 server_name 的站点配置。
  • 证书有效期 90 天，剩余 30 天时自动续期；apt 路线用 certbot.timer、snap 路线用 snap.certbot.renew.timer，每天检查两次。
  • **装完当天必须跑一次 sudo certbot renew --dry-run**，看到成功提示才算真正配好；不要用 --force-renewal 测试。
  • Let’s Encrypt 已停止发送过期提醒邮件，续期不能只靠定时器，加一层外部监控（UptimeRobot 或巡检里查过期时间）。
  • 续期后 Nginx 要重载才生效；certonly / webroot 方式记得配 deploy 钩子。

HTTPS 配好之后，部署链路就完整了：多阶段构建出瘦镜像 → Compose 编排起整个应用栈 → Nginx 反向代理对外服务 → Certbot 给流量加上 HTTPS。下一篇可以继续往上走一层：给这套部署加上最基础的监控与告警，让服务器出问题时先收到通知，而不是等用户来报。
