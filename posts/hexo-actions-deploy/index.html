GitHub Actions 自动部署 Hexo 博客到 GitHub Pages

发表于2026-11-09|更新于2026-11-09|部署
|总字数:1.7k|阅读时长:6分钟|浏览量:
文章摘要

写 Hexo 博客最烦的环节不是写文章，而是部署：本地 hexo clean && hexo generate && hexo deploy 三连击，换台电脑还要重装环境、重新配 Token，偶尔还会在部署那一步翻车。

更省事的做法是把部署交给 GitHub Actions：博客源码推到 GitHub，Actions 自动构建、自动发布。之后写文章的流程只剩两步：写 Markdown，git push。本文以官方文档为准，给出一份可直接照抄的工作流配置。

为什么用 GitHub Actions，而不是 hexo deploy

方式 优点 缺点
hexo deploy 一命令部署 本地一条命令搞定 需装 hexo-deployer-git、配 Token，换电脑要重配
GitHub Actions 自动部署 推送即发布，不依赖本地环境，私有仓库同样可用 首次要写一份工作流文件

如果你已经把博客源码放在 GitHub 上，Actions 是更省心的选择；如果你不想把源码上传到 GitHub，可以继续用一命令部署（见文末）。

第一步：把 Pages 源切换为 GitHub Actions

这份工作流分两个任务：

  • build：检出源码 → 安装指定版本的 Node.js → 安装依赖 → 执行 npm run build 生成静态文件 → 把 public/ 打包成 Pages 产物。
  • deploy：等 build 成功后，把产物发布到 GitHub Pages，并在 Actions 界面显示发布后的网址。

几个容易忽略的点：

  • npm run build 对应脚手架自带的 "build": "hexo generate"。如果你的 package.json 里没有 build 脚本，把这一步改成 run: npx hexo generate。
  • actions/cache@v4 缓存的是 node_modules，依赖不变时可跳过重复安装，构建更快。
  • deploy 任务的 permissions 必须保留 pages: write 和 id-token: write，否则没有发布权限。

第三步：提交推送，验证部署

推送后进入仓库 Actions 页面，能看到名为 Pages 的工作流正在运行：

  1. 等 build 任务变绿，说明 Hexo 已成功生成静态文件。
  2. 等 deploy 任务变绿，说明已发布到 GitHub Pages。
  3. 打开 https://<username>.github.io，确认新文章已上线。

常见问题排查

构建失败，先看日志定位到哪一步

Actions 页面点进失败的那次运行，红色叉号所在的步骤就是出问题的环节：Install Dependencies 失败多半是依赖问题，Build 失败多半是文章或主题配置问题。

本地能生成，Actions 构建失败

先核对工作流里的 node-version 是否和本地主版本号一致。Hexo 对 Node.js 版本有要求，版本差一个主版本就可能导致依赖装不上或生成报错。

推送了文章，线上没有更新

按顺序检查三点：

  1. Pages 的 Source 是否已改为 GitHub Actions（第一步）。
  2. Actions 里那次运行是否全部变绿，有没有失败的任务。
  3. public/ 是否被误提交进了仓库——它应该只由 Actions 生成。

构建卡住不动

GitHub Pages 构建偶尔会卡住或超时，先在 Actions 页面点 Re-run jobs 重跑一次，多数情况下重跑就能通过；连续多次在同一位置失败，再去看日志找原因。

小结

  • 源码推 GitHub + Actions 自动构建发布，是目前维护 Hexo 博客最省心的方式：一次配置，之后只管写文章和 git push。
  • 工作流以 Hexo 官方文档为准，关键点是 Node.js 版本与本地对齐、deploy 任务保留发布权限、Pages 源切换为 GitHub Actions。
  • 用自定义域名时，记得把 CNAME 文件放在 source/ 目录下，否则每次部署都会丢域名设置。
