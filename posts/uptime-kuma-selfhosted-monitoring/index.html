网站上线了，怎么知道它挂了？用 Uptime Kuma 自建服务监控

发表于2026-11-27|更新于2026-11-27|部署
|总字数:3.5k|阅读时长:12分钟|浏览量:
文章摘要

前面几篇把网站从零部署到了线上：Docker 多阶段构建瘦镜像、docker-compose 编排 Next.js + Postgres + Redis、Nginx 反向代理、Let’s Encrypt 配 HTTPS。站点跑起来了，但还有一个问题没解决——它半夜挂了，你怎么知道？

最常见的发现方式是用户先发现：群里有人说网站打不开了，你才后知后觉去重启。监控要解决的就是这个：服务一出问题，几十秒内通知到你；恢复了，再通知你一声。

方案有两个：用现成的 SaaS（比如 UptimeRobot，免费版对个人够用），或者自己搭一个开源的。本文讲后者——Uptime Kuma。它是一个单容器的开源监控工具，GitHub 约 9.2 万 star，Docker Hub 拉取超 1.9 亿次，功能足够个人和小团队用：HTTP、TCP、Ping、关键字、Push 心跳等多种监控类型，Telegram、Discord、邮件等几十种通知渠道，还能生成对外展示的状态页。整个部署十分钟左右，正好接上前面几篇的 Docker + Nginx + HTTPS 这一套。

先想清楚：监控放哪里

动手之前先定一个原则：监控不要和被监控的服务放在同一台服务器上。监控和网站同生共死——服务器一挂，监控也跟着挂，告警根本发不出去，等于没监控。

正确的做法：

  • 有多台服务器（比如前面文章里的几台 GCP 轻量机），把 Kuma 放在其中一台上，监控其他服务器上的服务；
  • 只有一台服务器，也可以在这台上跑 Kuma 监控本机服务，但要明白它的上限：它能发现应用挂了、端口不通了，发现不了整台机器断网、宕机；
  • 再进一步，给 Kuma 本身留一个外部兜底：用 UptimeRobot 免费版从外部盯着 Kuma 的地址，Kuma 挂了至少还有一层通知。

本文假设你有一台已经装好 Docker 和 Nginx 的服务器（前面几篇的环境），在这台上部署 Kuma。

这里有四个细节，照抄配置时容易忽略：

  1. 镜像标签用 :2，不要用 :latest。latest 标签已经被废弃，至今仍指向不再维护的 1.x（1.23.x）；:2 才是当前 2.x 稳定线。截至 2026 年 11 月底，2.x 最新版是 2.5.12（2026-11-17 发布，含一个安全修复），用 :2 会自动跟随 2.x 的小版本更新。想钉死版本也可以写 louislam/uptime-kuma:2.5.12。
  2. 端口绑 127.0.0.1:3001:3001，不要写成 3001:3001。Docker 发布的端口走 iptables 链，会绕过 ufw 的规则——3001:3001 等于把管理后台直接暴露在公网，任何人打开都能进初始设置向导、把自己设成管理员。绑到回环地址后，只有本机和反代能访问，公网入口只剩后面配的 Nginx。
  3. 数据卷 ./data:/app/data 必须落在本地磁盘。Kuma 默认用 SQLite，数据就存在 /app/data/kuma.db 里。SQLite 要靠 POSIX 文件锁，NFS 之类的网络文件系统不支持，会出奇怪的问题。
  4. **时区设成 TZ=Asia/Shanghai**，否则监控记录和告警里的时间都是 UTC，对不上你的直觉。

首次打开：选数据库、建管理员

浏览器打开 http://服务器IP:3001，2.x 的首次设置分两步：

  1. 选数据库。三个选项：SQLite（默认，单文件，个人用足够）、内嵌 MariaDB、外部 MariaDB/MySQL。个人或小团队直接选 SQLite，不用多想；只有监控点上千、历史数据量很大的场景才需要考虑 MariaDB。
  2. 建管理员账号。用户名、密码，顺手开双因素认证（2FA）。这一步不要拖——在配好反代、关掉直接访问之前，越早建好账号越安全。

这段配置里最容易踩的坑是 WebSocket。Kuma 的界面是实时应用，靠 Socket.IO 推心跳和图表数据，proxy_http_version 1.1 加 Upgrade / Connection 这两行就是让 Nginx 把 WebSocket 连接升级过去。漏了它们，页面能打开、登录也没问题，但仪表盘会一直停在 “Connecting…”，心跳数据永远不刷新，浏览器控制台里能看到 WebSocket connection ... failed 的 400 报错。

另外三个小设置：

  • proxy_pass 写 127.0.0.1，不要写 localhost。Debian 上 localhost 也可能解析到 ::1，Nginx 日志里会多一堆报错。
  • Host 头必须原样透传。Kuma 从 1.23.9 起会校验 WebSocket 的 Origin 和 Host 是否一致，对不上直接拒绝连接，日志里是 Origin (...) does not match host。
  • 进 Kuma 设置里开「反向代理 → Trust Proxy」，再把「通用 → Primary Base URL」填成 https://status.example.com。前者让 Kuma 拿到真实客户端 IP 而不是反代的 IP，后者让 Push 监控生成的 URL 用正确的域名。
  • 不要用子路径。example.com/kuma 这种挂法 Kuma 不支持，必须用单独的子域名。

加监控：先配这五种

监控项在仪表盘点「添加监控项」。默认每 60 秒检查一次，大部分场景不用改这个间隔。下面五种按需搭配，基本能覆盖个人项目：

监控类型 用来盯什么 关键配置
HTTP(s) 网站、API 接口是否正常返回 URL、期望状态码（默认 2xx）、关键字
HTTP(s) - 关键字 页面能打开，但内容被篡改、变空白页 关键字填页面上一定会有的文字
TCP / Ping 端口通不通、机器在不在线 主机名/IP + 端口
Push 定时任务、备份脚本跑没跑 Kuma 给一个 URL，任务成功后 curl 它
Docker 容器 容器是不是还在运行 需挂载 /var/run/docker.sock（只读）

逐个讲讲要点：

HTTP(s) 监控是最常用的。填网站首页 URL 就行。如果只想确认“服务还活着”，可以单独建一个轻量的健康检查接口（比如返回 {"ok": true} 的 /api/health），别拿首页大页面做高频检查——既省流量，判断也更干净。期望状态码默认接受 2xx；接口返回 301 也算正常的话，把接受范围加上。

关键字监控防的是“假活”。服务没挂、HTTP 200 正常返回，但页面内容被清空、反代配错返回了默认页，光看状态码发现不了。在关键字里填页面上一定会有的文字（比如网站名、版权行），内容对不上就报警。

Push 监控是给定时任务用的。备份脚本、定时同步、爬虫任务——这些东西的特点是“没跑你也不知道”。做法反过来：Kuma 给你一个 URL，任务跑完成功后 curl 一下这个 URL；超过设定的间隔没收到推送，Kuma 就判定任务出问题了。备份任务尤其值得配一个 Push 监控。

接 Telegram 告警：挂了第一时间知道

监控配好了，告警通道才是关键——告警发到一个你不看的地方，等于没配。Kuma 内置几十种通知方式，个人用最顺手的是 Telegram：免费、推送快、手机一定装着。

步骤：

  1. 在 Telegram 里找 @BotFather，发 /newbot，按提示起个名字，拿到一串 Bot Token；
  2. 给你刚建的 Bot 发一条任意消息；
  3. 浏览器打开 https://api.telegram.org/bot<你的Token>/getUpdates，在返回的 JSON 里找到 chat 下的 id，这就是你的 Chat ID；
  4. 回到 Kuma：设置 → 通知 → 添加通知 → 选 Telegram，填 Bot Token 和 Chat ID；
  5. 点「测试」，手机上收到测试消息才算通。

每个监控项可以单独指定用哪个通知渠道，也可以全站默认一个。建议：所有监控项都挂上通知，并且真的点一次「测试」。没验证过的告警通道是最危险的——它让你以为有人在盯着，实际上什么都没发出去。

除了 Telegram，常用的还有 Discord（Webhook 一行就能接）、邮件（SMTP）、Gotify（自建推送）。选你手机上一定会看到的那一个。

开一个公开状态页

很多服务都有自己的状态页（status.example.com），出问题时用户先去那里看，而不是来问你。Kuma 自带这个功能：

设置 → 状态页 → 新建，起个名字（比如“服务状态”），把要公开的监控项勾上，选一个域名或用默认路径访问。

几点提醒：

  • 状态页默认是公开的，勾监控项时想清楚——只放用户关心的（网站、API），别把内网数据库、后台管理地址也公开了；
  • 可以给状态页设密码，只对内部分享；
  • 状态页本身也要被监控（用 UptimeRobot 免费版从外部盯着 Kuma 的地址），否则状态页挂了你都不知道。

常见问题

页面能打开，但一直显示 “Connecting…”

反代没透传 WebSocket。检查 Nginx 配置里有没有 proxy_http_version 1.1、Upgrade 和 Connection "upgrade" 这三行，以及 Host 头是不是原样透传。改完 nginx -t && systemctl reload nginx。

监控容器里跑的服务，填 localhost 总是失败

容器里的 localhost 是容器自己，不是宿主机。监控宿主机上的服务有两个办法：填宿主机的 Docker 网关 IP（docker network inspect uptime-kuma_default --format '{{(index .IPAM.Config 0).Gateway}}' 查），或者填 host.docker.internal（Docker Desktop 自带，Linux 上 Docker 20.10+ 也支持）。

UFW 明明封了 3001，外网还是能打开 Kuma

不是 UFW 坏了，是 Docker 发布的端口绕过了它。这是本文开头就让端口绑 127.0.0.1 的原因——补救办法就是把 Compose 里的端口改成 "127.0.0.1:3001:3001" 再 docker compose up -d，而不是去调防火墙规则。

监控项频繁误报 DOWN，几分钟后又自己恢复

先把重试次数设成 1~2 次；再看是不是检查间隔设得太短（比如 20 秒一次），目标服务器扛不住这个频率；最后看是不是 Kuma 所在的机器本身网络不稳——监控端网络抖，报出来的全是假警报。

Kuma 所在的服务器挂了怎么办

这是自建监控的固有上限：监控挂了，告警发不出去。所以开头那句话再重复一遍：再用一个外部服务（UptimeRobot 免费版）从外部盯着 Kuma 本身。两层监控，互相兜底。

小结

整套流程串起来就是：

  1. 监控单独放一台服务器，别和被监控服务同生共死；
  2. louislam/uptime-kuma:2 + ./data:/app/data + 127.0.0.1:3001 部署，选 SQLite、建管理员、开 2FA；
  3. Nginx 反代配 HTTPS，WebSocket 升级头和 Host 头不能漏，Kuma 里开 Trust Proxy、填 Primary Base URL；
  4. HTTP、关键字、TCP/Ping、Push、Docker 容器五种监控按需配，重试 1~2 次防误报；
  5. Telegram 告警接好并点一次「测试」，再开一个公开状态页；
  6. 定期停容器备份 kuma.db，升级前先备份。

部署、反代、HTTPS、监控，这四篇连起来，就是一套个人项目从“能跑”到“跑得住”的完整链路。网站上线只是开始，知道它什么时候挂、挂了多久，比多加一个功能重要得多。

上一篇讲了怎么用 Nginx 给 Next.js 应用做反向代理，但那篇文章里的站点跑的还是 HTTP。HTTP 有两个现实问题：浏览器会在地址栏标“不安全”，用户不敢输密码、填表单；搜索引擎也明确把 HTTPS 作为排名信号之一。好在今天给网站上 HTTPS 不用再花钱买证书——Let’s Encrypt 免费签发，Certbot 全程自动，一台服务器十分钟就能搞定。 下面以前一篇的 Nginx 站点为例，从零配到自动续期。 先确认三个前置条件动手之前先把这三件事对上，缺一个后面都会卡住： 域名已经解析到这台服务器。用 dig +short example.com 或 ping example.com 看返回的 IP 是不是服务器的公网 IP。域名没解析过来，Let’s Encrypt 连不上你的服务器，验证一定失败。 Nginx 在跑，且 80 端口对外放行。Let’s Encrypt 用 HTTP-01 方式验证域名所有权：它会在你的服务器上放一个临时文件，再从公网经 80 端口来取。防火墙（UFW、云厂商安全组）把 80 封了，验证就过不去。配好 HTTPS 之后...
